# 지형 — 모래 붕괴 자동자

이 프로젝트의 심장. **서버(numpy)와 클라이언트(TypedArray)가 비트 단위로 동일한 결과**를 내야 한다.
한쪽이라도 다르면 두 플레이어가 서로 다른 지형을 보게 되고, 그 순간 게임이 끝난다.

> **참조 구현.** `tools/sandbox/automaton.js` 가 이 문서의 구현이다.
> 문서와 코드가 어긋나면 문서를 먼저 고친다. 이 문서의 수치는 **`tools/sandbox/harness.mjs` 로 실측한 값**이며,
> Phase 0 에서 §3.1 의 규칙 조합이 주장대로 동작하는지 확인했다. §11 에 실측표가 있다.

## 1. 격자

```
맵          1920 × 1080 px
셀 크기      2 px
격자         960 × 540 = 518,400 셀
저장         Uint8Array(518400), row-major   idx = y * 960 + x
y축          아래로 증가 (y=0이 하늘, y=539가 바닥)
```

**2px를 고른 이유.** 1px면 208만 셀이라 JS 쪽에서 부담스럽고, 4px면 붕괴가 뭉텅이로 보여 모래 느낌이 죽는다.
2px는 렌더링에서 마칭 스퀘어로 매끈하게 펴면 눈에 셀이 안 보이면서 물리는 충분히 촘촘하다. `docs/rendering.md` §4.

### 1.1 격자 경계 — 규칙별로 명시한다

**"격자 밖은 EMPTY"만으로는 구현이 갈라진다.** `idx = y*960 + x` 를 그대로 쓰면 `x=-1` 이
직전 행의 오른쪽 끝(`idx = y*960 - 1`)을 가리켜 흙이 화면을 감아 돌며 텔레포트한다.
그래서 경계를 **인덱스 산술이 아니라 조건 분기로** 처리한다.

| 위치 | 조건 평가 시 | 목표 셀이 그쪽일 때 |
|---|---|---|
| `x < 0` 또는 `x > 959` | `EMPTY` 로 읽는다 | 이동은 성립하고, **소멸**한다 (`dst = VOID`) |
| `y > 539` | `EMPTY` 로 읽는다 | 이동은 성립하고, **소멸**한다 (`dst = VOID`) |
| `y < 0` | 발생하지 않는다 (위로 가는 규칙이 없다) | — |

**소멸의 커밋 절차:** `grid[src] = EMPTY` 만 실행하고 목표에는 아무것도 쓰지 않는다.
격자 밖 목표는 여러 셀이 동시에 지목할 수 있으므로 **해소(§3.2)를 거치지 않고 곧바로 승자로 처리한다.**
경합이 존재하지 않기 때문이다.

**흙이 화면 밖으로 떨어져 사라지는 건 정상 동작이다.** 좌우 벽에 반사시키지 않는다.

> ⚠️ **그래서 맵 생성기가 좌우 끝을 반드시 봉인해야 한다.**
> 최외곽 열의 낙하 재질은 `dir` 이 격자 밖(= `EMPTY`)이라 절반의 확률로 매 스텝 흘러나간다.
> 봉인하지 않고 `hills` 프리셋을 정착시킨 실측:
>
> | | 정착 스텝 | x=0 표면 |
> |---|---|---|
> | 봉인 없음 | 21,728 | 322 px → **652 px** (300 px 침식) |
> | 봉인 | **1,327** | 514 px → 514 px (4 px) |
>
> 맵 양끝에 300 px 구멍이 파이고, 그 위로 쏜 포탄이 지형에 맞지 않고 격자 밖으로
> 빠져나가 **게임이 성립하지 않았다.** 정착 비용의 94% 도 이 유출이 만든 것이었다.
>
> **규칙:** 최외곽 **2열**을 그 열의 표면부터 바닥까지 `BEDROCK` 으로 채운다.
> `BEDROCK` 은 낙하하지 않는 비-`EMPTY` 장애물이라 안쪽 흙의 `dir == EMPTY` 조건이
> 깨져 유출이 원천 차단된다. 구현은 `tools/sandbox/lab.js` 의 `sealEdges()`.
> `decisions.md` B1-4.

## 2. 재질

```typescript
enum Material {
  EMPTY   = 0,  // 공기
  SAND    = 1,  // 모래·표토.   낙하 + 완만한 안식각
  SOIL    = 2,  // 점토·심토.   낙하 + 급한 안식각
  SCREE   = 3,  // 자갈.        낙하 + 45° 고정
  ROCK    = 4,  // 암반.        낙하 안 함. 단, 기반암과 끊기면 붕괴
  BEDROCK = 5,  // 기반암.      불변. 파괴 불가, 이동 불가
}
```

| 재질 | 낙하 | 적용 규칙 | 안식각(실측) | 폭발 저항 | 역할 |
|---|---|---|---|---|---|
| `SAND` | ✅ | 1, 2, 3 | **26.6°** | 낮음 | 지표층. 잘 무너지고 넓게 흐른다 |
| `SOIL` | ✅ | 1, 2, 3 | **40.3°** | 중간 | 중간층. 급한 벽을 만든다 |
| `SCREE` | ✅ | 1, 2 | **44.2°** | 낮음 | `ROCK` 붕괴의 산물. 각진 더미를 만든다 |
| `ROCK` | ❌ | — | — | 높음 | 오버행과 아치를 만든다. §6 |
| `BEDROCK` | ❌ | — | — | ∞ | 맵의 골격 앵커 |

**`ROCK` 과 `BEDROCK` 은 제안 단계에서 이동 후보가 아니지만, 다른 셀의 모든 조건 평가에서
비-`EMPTY` 장애물로 읽힌다.** 명세에 없으면 한쪽이 `SCREE` 를 통과시키는 구현을 만들 수 있다.

**재질 3종(SAND/SOIL/SCREE)이 서로 다른 각도로 쌓이는 것**이 지층 노출 연출과 직결된다.
구덩이를 파면 완만한 모래 경사 밑에서 각진 점토 벽이 드러나고, 그 밑에서 암반이 나온다.
이 시각적 보상이 파괴 행위 자체를 재밌게 만든다.

**세 각도는 정적 게이트로 분리한다** (§4.2). 실측 `SCREE 44.2° > SOIL 40.3° > SAND 26.6°` 로
지층이 눈에 구분된다. `harness.mjs --repose` 가 이 순서를 상시 검증한다.

## 3. 자동자 — 제안/해소 2단계 (절대 규칙 3)

> **셀을 순회하면서 그 자리에서 옮기는 방식을 금지한다.**
> 그렇게 하면 순회 순서가 결과를 바꾸고, numpy 벡터 구현과 TS 루프 구현이 절대 일치하지 않는다.

한 스텝은 반드시 아래 세 단계로만 구성된다. **Propose 는 격자를 읽기만 하고, Commit 만 격자를 쓴다.**

### 3.1 Phase 1 — Propose

모든 셀이 **동시에** 이동 목표를 계산한다.

낙하 재질에 대해 아래 규칙을 **순서대로** 적용하고, 처음 성립하는 것을 채택한다.

| 우선 | 규칙 | 조건 | 결과 |
|---|---|---|---|
| 1 | **자유낙하** | `below == EMPTY` | ↓ |
| 2 | **대각 미끄러짐** | `belowDir == EMPTY` **AND** `dir == EMPTY` | ↘ 또는 ↙ |
| 3 | **완만 활강** | `dir == EMPTY` AND `dir2 == EMPTY` AND `belowDir2 == EMPTY` | → 또는 ← (한 칸) |

- 규칙 2에서 `dir == EMPTY`를 함께 요구하는 이유: 이게 없으면 모래가 1셀 틈으로 대각선 통과해 벽을 뚫는다
- **규칙 2까지만 쓰면 안식각 45°가 나온다.** 이웃 열의 낙차가 2 이상이면 규칙 2가 반드시 그 자리를 메우므로
  낙차 상한이 1로 강제되기 때문이다. **실측 44.2°, 최대 열간 낙차 1** — 기하 예측과 일치한다
- 규칙 3이 2:1 경사를 만들어 `atan(1/2)` = **26.57°** 까지 완만해진다. **실측 26.6°**

#### 방향 결정 절차

**의사코드로 못박는다.** "해시로 고른다"만 적으면 두 가지로 읽혀 구현이 갈라진다.

```
mat = grid[src]                             // 출처 셀의 재질. 임계값은 이것으로 정한다
if (mat is ROCK or BEDROCK or EMPTY) return 이동없음

// ── 규칙 1 (해시 불필요)
if (below == EMPTY) return 규칙1 → (x, y+1)

// 규칙 2·3 은 둘 다 dir 쪽 같은 행 셀이 EMPTY 인 것을 요구한다.
// 좌우가 모두 막혔으면 어떤 해시 값에서도 불가능하므로 즉시 종료한다 (§5.1 판정에 쓰인다).
if (left != EMPTY && right != EMPTY) return 이동없음

h    = hash32(seed, x, y, step)             // §7.1
side = h & 1                                 // 1 = 우, 0 = 좌
dir  = side ? +1 : -1

rule = dir 방향으로 규칙 2 → 규칙 3 순서로 검사한 첫 성립 (기하 조건만)
if (rule == 없음) return 이동없음           // ← 반대쪽은 시도하지 않는다 (확정)

// ── 확률 게이트는 규칙 3 에만 걸린다. 규칙 2 에는 걸지 않는다.
if (rule == 3) {
    thr = SLIDE_CHANCE_Q8[mat] << 8          // SCREE 는 0 → 규칙 3 을 절대 못 쓴다
    if (((h >>> 8) & 0xFFFF) >= thr) return 이동없음   // 폴백 없음. 이번 스텝은 정지
}
return rule
```

**게이트에 대해 못박는 다섯 가지.** 이게 없으면 옮겨 쓸 때 갈라진다.

1. 게이트는 **규칙 3 에만** 걸린다. 규칙 2 에 걸면 `SCREE` 의 45° 상한이 무너진다
2. 임계값은 **출처 셀의 재질**로 정한다 (목표 셀이 아니다)
3. 게이트 실패는 **"이번 스텝 이동 없음"** 이다. 다른 규칙이나 반대 방향으로 폴백하지 않는다
4. `SCREE` 가 규칙 3 을 안 쓰는 것은 `SLIDE_CHANCE_Q8[SCREE] = 0` 으로 표현한다.
   §2 의 "적용 규칙" 열과 같은 뜻이며, 의사코드가 재질 분기를 따로 갖지 않게 한다
5. 게이트 판정은 §3.2 우선순위 계산 **전**이다. 게이트에 막힌 셀은 제안 자체를 만들지 않는다

**게이트 해시는 `step` 을 쓰지 않는다** (§4.2, §7.1). 위 의사코드의 `h` 대신
`hash32(seed ^ 0x9E3779B9, x, y, 0)` 을 쓰며, §5.1 의 가동 판정에도 이 게이트를 포함한다.

#### 방향은 한쪽만 시도한다

- **확정 규칙이다** (`decisions.md` A2). 고른 방향이 막혀 있으면
  반대쪽이 열려 있어도 이번 스텝에는 움직이지 않는다. `step` 이 바뀌면 `side` 도 바뀌므로
  다음 스텝에 반대쪽을 시도하게 된다. 모래가 물처럼 흐르지 않고 사각사각한 감각이 나오고,
  벡터 구현이 마스크 1세트로 끝난다
- 규칙 2와 규칙 3은 **같은 `side` 비트를 공유한다.** 규칙 2가 실패했을 때 규칙 3이 다른 방향으로
  성립하는 것을 허용하지 않는다
- 양방향 시도는 유동을 약 2배 빠르게 만들지만 채택하지 않았다. 비교용 토글은 샌드박스에 남아 있다

### 3.2 Phase 2 — Resolve

여러 셀이 같은 목표를 제안할 수 있다. **결정론적 우선순위**로 하나만 이동시킨다.

```
prio(src → dst) = (ruleWeight << 17) | ((side ^ flipBit(dst)) << 16) | (hash32(src) & 0xFFFF)

ruleWeight   규칙1 → 3,  규칙2 → 2,  규칙3 → 1        ← 규칙번호의 역순이다
flipBit(dst) hash32(seed, dstX, dstY, step) & 1
```

1. 각 목표 셀에 대해 제안자들의 `prio` 최댓값을 구한다 (numpy: `np.maximum.at`)
2. 자기 `prio`가 목표의 최댓값과 같은 제안자만 이동한다
3. 나머지 제안자는 이번 스텝에 제자리에 남는다

> **가중치는 규칙번호의 역순이다.** 규칙 1(자유낙하)이 규칙 2·3보다 항상 이겨야 하는데
> 해소가 최댓값 승자이므로, 규칙번호를 그대로 쓰면 규칙 3이 이겨 의도와 정반대가 된다.
> 떨어지는 흙이 옆에서 미끄러져 오는 흙보다 우선하는 것이 물리적으로 자연스럽고,
> 구현상 우선순위 뒤집힘도 막는다.

**규칙 1의 하위 17비트는 0으로 두어도 결과가 같다.** 규칙 1의 목표는 항상 `(x, y+1)` 이라
제안자가 유일하고, 가중치가 규칙 2·3보다 크기 때문이다. 대형 붕괴에서 자유낙하가 지배적이므로
이 최적화로 해시 2회를 아낀다. 서버가 이 최적화를 쓰든 안 쓰든 결과는 동일하다.

#### 동점은 왜 불가능한가

**`hash16` 만으로는 동점을 막을 수 없다.** 16비트 값공간은 65,536개인데 셀은 518,400개라
비둘기집 원리로 충돌이 확정이며, 대형 붕괴에서 스텝당 경합 목표가 1,000개면
600스텝당 기대 동점이 약 18회다. 동점이 나면 한 목표에 두 셀이 들어가 **질량이 사라지고**,
어느 재질이 남는지가 순회 순서에 의존한다 — 절대 규칙 3이 막으려던 것이 정확히 여기서 되살아난다.

그래서 우선순위에 **방향 비트**를 넣는다. 한 목표 셀 `D = (dx, dy)` 를 노리는 제안자는 최대 5개다.

| 규칙 | 제안자 | `side` |
|---|---|---|
| 1 | `(dx, dy-1)` | — (유일) |
| 2 | `(dx-1, dy-1)` / `(dx+1, dy-1)` | 1 / 0 |
| 3 | `(dx-1, dy)` / `(dx+1, dy)` | 1 / 0 |

같은 `ruleWeight` 안에서 경합하는 제안자는 **정확히 2개이고 `side` 가 반대**다.
따라서 `side` 비트만으로 승자가 유일하게 결정되고 **동점이 구조적으로 불가능하다.**
`flipBit(dst)` 를 XOR 하는 이유는 좌우 편향 제거다 — `side` 만 쓰면 항상 오른쪽에서 온 흙이 이겨
더미가 한쪽으로 흐른다. `flipBit` 은 목표 셀에만 의존하므로 두 경합자가 같은 값을 본다.

**이 성질은 테스트로 강제한다.** `tools/sandbox/harness.mjs --determinism` 의 동점 검출이
`layers`/`hills`/`arch`/`collapse` 4개 시나리오 × 150스텝에서 동점 0건을 확인한다.

### 3.3 Phase 3 — Commit

```
1) 승자 전체에 대해  grid[src] = EMPTY
2) 승자 전체에 대해  grid[dst] = mat(src)     // mat 은 1) 이전에 캡처한 값
```

**두 패스로 나눈다.** 제안 조건이 목표의 사전 상태 `EMPTY` 를 요구하므로 `src` 집합과 `dst` 집합은
서로소이고, 따라서 한 패스로도 결과는 같다. 그래도 나누는 이유는 순서 의존이 끼어들 여지를 원천 차단하는 것이다.

### 3.4 서브스텝 — 렌더 전용

```
1 렌더 프레임 = SUBSTEPS 회 자동자 스텝   (§4 참조)
```

> **`SUBSTEPS` 는 시뮬레이션 상수가 아니라 표현 상수다.**
> 자동자 스텝 시퀀스는 `SUBSTEPS` 와 무관하게 정의되고(정착 조건까지 반복), `SUBSTEPS` 는
> 클라이언트가 한 프레임에 몇 스텝을 소비해 보여줄지만 정한다.
> 따라서 `SUBSTEPS` 를 바꿔도 **격자 결과와 체크섬은 변하지 않는다.** 벽시계 재생 속도만 바뀐다.
> 서버는 프레임이 없으므로 `SUBSTEPS` 를 아예 쓰지 않는다.

셀 단위 속도/가속도는 **넣지 않는다.** 서브스텝 횟수로만 조절한다.
근거: 셀별 속도를 넣으면 상태가 커지고(속도 배열 추가) 결정론 관리 지점이 두 배가 된다.

## 4. 상수 — 실측으로 정한 값과 아직 못 정한 값

### 4.1 표

| 상수 | 값 | 근거 |
|---|---|---|
| `SLIDE_GATE_STATIC` | **1** (확정) | 게이트 해시에서 `step` 을 뺀다. §4.2, `decisions.md` A1 |
| `SUBSTEPS` | **미확정 (11~27)** | 최대 무기는 11, 동시 폭발 최악(4,846스텝)은 27 이 필요하다. §11.2·§11.6 |
| `SLIDE_CHANCE_SAND_Q8` | 256 (= 100%) | 26.6° 를 목표로 하면 이 값. 낮춰도 각도는 안 바뀐다 — §4.2 |
| `SLIDE_CHANCE_SCREE_Q8` | **0** (확정) | 규칙 3 미적용을 이 값으로 표현한다 (§3.1 게이트 5번) |
| `SLIDE_CHANCE_SOIL_Q8` | 48 | 40.3°. 값은 밸런싱이지만 조절 **방법**은 확정이다 (§4.2) |
| `MAX_SETTLE_STEPS` | **미확정 (12,000 권장)** | 관측 최악 4,846스텝(§11.6) × 여유. 600은 반경 20조차 못 담는다 |
| `CONNECTIVITY_MAX_ROUNDS` | **미확정** | §6.1 재개 루프 상한. 통상 2회로 끝난다 |
| `STABLE_FRAMES` | 삭제 | §5.2 의 정착 판정이 정확해져 불필요해졌다 |

**`SUBSTEPS = 28` 은 렌더 예산 경계에 딱 걸린다.** 스텝당 비용이 약 0.174 ms 이므로
프레임당 `28 × 0.174 = 4.9 ms` 로 `docs/rendering.md` §8 의 5 ms 예산 안이지만 여유가 없다.
17 이면 2.9 ms 로 넉넉한 대신 최악 케이스가 4.8초 걸린다. `decisions.md` A3.

`slideChance` 는 **Q8 정수(0~256)** 다. `docs/simulation.md` §2.1 이 부동소수점을 금지하므로
`0.75`·`0.15` 같은 실수 표기를 쓰지 않는다. `0.15 × 65536 = 9830.4` 처럼 정수가 아닌 값이 나오면
한쪽이 floor, 다른 쪽이 round 를 써서 갈라진다. 게이트는 §7.1.

**`SUBSTEPS` 는 이 표에 있지만 시뮬레이션 상수가 아니다.** §3.4 대로 표현 상수이므로
클라이언트에만 존재하고, `server/src/talus/constants.py` 와 `SIM_VERSION` 해시에 들어가지 않는다.
들어가면 `SUBSTEPS` 만 다른 두 클라이언트가 같은 방에 못 들어가 — 저사양 기기가 값을 낮추는 것을
막아버린다. `server/tests/test_determinism.py::test_presentation_constants_are_not_in_sim_version`
이 이를 강제한다.

### 4.2 게이트에서 `step` 을 빼야 `slideChance` 가 안식각을 조절한다 — 확정

이전 판 문서는 "확률이 낮을수록 더 급한 경사에서 멈춘다 → 안식각이 연속적으로 조절된다"고 적었다.
**틀렸다.** 실측 결과다 (`harness.mjs --sweep`).

| `SLIDE_CHANCE_SAND_Q8` | 안식각 | 정착 스텝 |
|---|---|---|
| 0 | 44.2° | 3,727 |
| 8 (3.1%) | **26.6°** | 48,026 |
| 64 (25%) | **26.6°** | 10,837 |
| 192 (75%) | **26.6°** | 6,796 |
| 256 (100%) | **26.6°** | 6,166 |

게이트 입력에 `step` 이 들어 있으므로, 이번 스텝에 막힌 셀도 다음 스텝에는 통과한다.
즉 **확률이 0보다 크면 결국 반드시 미끄러지고**, 종단 안식각은 규칙 3의 기하 한계(26.57°)로 수렴한다.
`slideChance` 가 바꾸는 것은 **정착 속도뿐**이다 (48,026 → 6,166, 7.8배).

이전 문서의 직관이 맞아 보였던 이유는 §5.2 의 정착 판정 버그였다. "이동 셀 0" 을 정착으로 보면
낮은 확률에서 조기에 얼어붙어 급한 경사가 남는다. 판정을 고치자 이 효과가 사라졌다.

**그래서 게이트에서 `step` 을 뺀다 — 이것이 확정 규칙이다** (`decisions.md` A1).
활강 가능 여부가 위치로 고정되어
"잘 안 미끄러지는 자리"가 사면을 붙잡는다. 실측:

| `Q8` | 0 | 16 | 32 | 48 | 64 | 96 | 128 | 160 | 192 | 224 | 256 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 안식각 | 44.2° | 44.0° | 41.2° | **40.3°** | 40.2° | 37.1° | 35.8° | 32.8° | 30.9° | 28.2° | **26.6°** |
| 정착 스텝 | 3,727 | 3,971 | 4,582 | 4,478 | 4,705 | 4,755 | 4,977 | 5,370 | 5,616 | 5,981 | 6,166 |

44.2°~26.6° 가 **단조 연속으로** 조절되고, 정착도 전 구간에서 수렴하며 step 게이트보다 빠르다.
현재 채택값은 `SAND 256 → 26.6°`, `SOIL 48 → 40.3°`, `SCREE 0 → 44.2°` 다.

`tools/sandbox` 의 **정적 게이트** 토글을 끄면 옛 동작(step 포함)을 비교해볼 수 있다.
규칙은 켠 쪽이다.

### 4.3 왜 문서로 못 정하는가

`slideChance`, `SUBSTEPS`, 재질별 규칙 조합이 게임 전체의 체감을 결정한다.
**이 값들은 `tools/sandbox/` 에서 손으로 만져보고 정한다.** 위 표는 "각도가 몇 도가 나오는가" 까지만 답한다.
"그 각도가 재밌는가" 는 실제로 파 보지 않으면 알 수 없다.

`tools/sandbox/` 는 다음을 갖춘다.

- 위 상수 전부를 실시간 슬라이더로 조절
- 마우스로 파기 / 재질별로 그리기 / 폭발 (반경 조절)
- 안식각 실측 — 기둥을 쌓아 무너뜨린 뒤 사면을 최소제곱 회귀로 각도 출력
- 정착까지의 스텝 수, 벽시계 ms, 순수 sim ms, 이동 셀 누적
- 결정론 자기검증 5종 (재현성 / 순서 독립성 / 동점 / 활성 행 무결성 / 해시 품질)
- 헤드리스 동일 검증: `node tools/sandbox/harness.mjs`

## 5. 활성 영역과 정착

전체 격자를 매 스텝 돌릴 이유가 없다. 대부분의 셀은 이미 안정 상태다.

### 5.1 활성 행 — "움직인 셀"이 아니라 "움직일 수 있는 셀" 기준

> **이전 판의 정의("활성 = 직전 스텝에 움직인 셀 ∪ 그 8이웃")는 틀렸다.**
> 그 정의는 규칙이 **상태만의 함수**일 때만 옳다. §3.1 의 규칙은 방향 선택과 `slideChance` 게이트가
> `step` 에 의존하므로 **상태 + 스텝**의 함수다. 움직일 수 있었지만 이번 스텝에 게이트나
> 방향 선택에 막힌 셀을 비활성으로 떨어뜨리면 **영구히 얼어붙는다.**
>
> 실측으로 확인했다. 활성 행 0으로 "정착" 보고된 격자에 전 행을 강제로 켜니 즉시 58셀이 움직이고,
> 723스텝 30,055회 이동이 더 필요했다. SCREE 더미가 45° 가 아니라 55° 에서 멈춘 원인이 이것이다.

**정의.** 제안 단계에서 각 낙하 재질 셀에 대해 **양방향을 기하로 평가**해
"어떤 해시 값에서든 움직일 수 있는가"(= **가동**, mobile)를 판정한다.

```
가동(cell) ⟺ 규칙 1 성립
           ∨ 좌 방향으로 규칙 2 또는 규칙 3 이 기하적으로 성립
           ∨ 우 방향으로 규칙 2 또는 규칙 3 이 기하적으로 성립
```

- 확률 게이트는 이 판정에서 **제외한다.** `step` 게이트는 언젠가 반드시 통과하기 때문이다.
  단 `slideChance == 0` 이면 규칙 3은 영구히 불가능하므로 제외한다
- 정적 게이트(§4.2)를 채택하면 게이트 통과 여부가 위치로 고정되므로 **판정에 포함해야 한다.**
  포함하지 않으면 정착이 영원히 성립하지 않는다
- 가동 셀이 있는 행에 대해 **`y-1 .. y+2`** 를 다음 스텝의 활성 행으로 켠다.
  규칙 3의 수평 도달 거리 2는 같은 행이라 자동으로 포함된다
- 폭발이 건드린 영역은 `y0-2 .. y1+2` 를 켠다. 연결성 검사가 `SCREE` 를 만든 영역도 켠다

구현은 **셀 단위 집합이 아니라 행(row) 단위 비트마스크**로 한다.

- numpy 슬라이싱과 궁합이 좋다
- TS 쪽도 행 범위 루프로 동일하게 처리된다
- 셀 단위 활성 집합은 두 구현의 순회 방식이 달라져 결정론 위험이 생긴다

**양쪽 구현은 정확히 같은 행 집합을 돌아야 한다.**

> ⚠️ **`min..max` 연속 구간으로 과대 포함하는 최적화를 금지한다.**
> "비활성 행을 추가로 도는 것은 결과를 바꾸지 않는다"는 §5.2 의 강제 종료와 양립하지 않는다.
> 강제 종료는 **가동 셀이 남은 격자**를 확정하므로 그 순간 "비활성 행에는 가동 셀이 없다"는
> 불변식이 깨진다. 그 뒤 서로 떨어진 두 구간에 폭발이 생기면(동시 턴이라 정상 상황이다 —
> 예: 행 98~142 와 행 398~442) 연속 구간을 슬라이스하는 구현은 행 300 에 얼어 있던 셀을
> 움직이고, 정확한 행 집합을 도는 구현은 움직이지 않는다. 같은 입력에서 격자가 갈라진다.
>
> 행은 540개뿐이라 불연속 구간을 행 루프 + 슬라이스로 처리하는 비용은 무시 가능하다.

**불변식:** 강제 종료가 없었다면, 모든 가동 셀은 항상 활성 행 안에 있다.
`harness.mjs --active` 가 매 스텝 `step().mobile` 과 격자 전체 스캔을 비교해 이를 검증한다.

리싱크 수신 측도 같은 규칙을 따른다 — `docs/netcode.md` §4.2 의 `fullState` 는 항상
**턴 확정 후 격자**이며, 수신 측은 활성 마스크를 **빈 상태로** 시작한다.
격자에서 마스크를 재계산하면 서버와 갈라진다.

### 5.2 정착 판정

```
정착 완료 ⟺ 가동 셀이 0개
```

**이건 근사가 아니라 정확한 판정이다.** 가동 셀이 0이면 어떤 해시 값에서도 아무 셀도 움직일 수 없다.
그래서 `STABLE_FRAMES` 같은 연속 관측 창이 필요 없다.

`MAX_SETTLE_STEPS` 에 도달하면 **강제 종료한다.**

- 종료 시점의 격자를 그대로 확정하고, **활성 행 마스크를 비운다**
- 즉 sim 상태는 격자 하나뿐이며 정착 스텝 카운터와 마스크는 턴을 넘기지 않는다.
  근거: 결정론 관리 지점을 최소화한다. 마스크를 상태로 유지하면 체크섬(§7.2)과
  `fullState`(`docs/netcode.md` §4.2)에 모두 실어야 한다
- 미세 진동으로 영원히 안 멈추는 구성이 반드시 생긴다. 그때 게임이 멈추면 안 된다

**정착이 길어지면 시간 압축을 적용한다.** 클라이언트가 프레임당 소비하는 스텝 수를 올려
시각적으로 배속한다. §3.4 대로 `SUBSTEPS` 는 표현 상수이므로 **시뮬레이션 결과는 동일하고,
양쪽 구현이 같은 압축 스케줄을 쓸 필요도 없다.** 압축 곡선은 §10 미결 4.

## 6. 암반 구조 붕괴

`ROCK`은 낙하 규칙을 적용받지 않아 오버행과 아치를 만든다.
하지만 아치의 다리를 부수면 천장이 공중에 떠 있게 된다. 그러면 안 된다.

### 6.1 연결성 검사

**모든 carve 가 끝난 뒤 무조건 1회, 그리고 정착이 끝날 때마다 1회 더 — 변환이 0 이 될 때까지.**
(이전 판은 §8-5 에서 "ROCK 을 제거했다면" 조건부로, 순서 블록에서는 "전부 끝난 뒤 1회" 로
서로 다르게 적어 두었다. 아래 루프로 통일한다.)

```
carve 전부 (슬롯 오름차순)
loop:
    변환 = 연결성 검사()
    정착()                                  // 가동 셀 0 까지, §5.2
    if (변환 == 0) break
    if (루프 회차 >= CONNECTIVITY_MAX_ROUNDS) break     // 상한. §10 미결
정착 완료 → 체크섬 1회 (§7.2)
```

- **`step` 카운터는 재개해도 리셋하지 않는다** (§7.1). 리셋하면 붕괴 패턴이 반복된다
- 재개 정착도 `MAX_SETTLE_STEPS` 예산을 **공유한다.** 각 재개마다 새로 주지 않는다
- 체크섬은 이 루프가 완전히 끝난 뒤 **정확히 한 번** 계산한다.
  첫 정착 직후에 계산하면 재개가 있는 턴에서 서버·클라가 다른 시점을 재게 된다
- `CONNECTIVITY_MAX_ROUNDS` 값은 미결이다 (§10 미결 9). 통상 2회로 끝난다

1. 모든 `BEDROCK` 셀을 시드로 잡는다
2. `ROCK` ∪ `BEDROCK`을 통해 **4방향 연결**로 flood fill
3. 도달하지 못한 `ROCK` 셀을 전부 `SCREE`로 변환한다
4. 변환된 셀들을 활성 영역에 추가한다 → 자동자가 무너뜨린다

> **4방향 연결로 고정한다.** 8방향이면 대각선 한 점으로 이어진 구조가 버텨서 부자연스럽다.
> 두 구현이 같은 연결성 정의를 써야 하며, **결과 집합만 같으면 되고 라벨링 순서는 상관없다.**
> 그래서 서버는 numpy 반복 전파, 클라는 스택 flood fill 로 구현해도 된다.

정착 후에도 검사하는 이유는 붕괴로 지지물이 흘러나가 새로 떠버린 `ROCK` 이 생길 수 있기 때문이다.

### 6.2 왜 이게 중요한가

무기 §6.1의 **성형탄**은 지형을 거의 안 파지만 데미지가 높다. 이걸 아치 다리에 쏘면 다리 몇 셀만 사라지고,
연결성 검사가 아치 전체를 `SCREE`로 바꿔 **수천 셀이 한꺼번에 무너진다.**

**실측으로 확인했다.** `overhang` 시나리오에서 캔틸레버 슬랩(11,840셀)을 지지하는 기둥에
반경 40 폭발 1발 → 연결성 검사가 `ROCK` 16,265셀을 `SCREE` 로 변환 → 슬랩이 전부 붕괴,
2,508스텝에 정착. 작은 원인이 거대한 결과를 만드는 이 장면이 이 게임에서 가장 극적인 순간이 될 것이고,
그래서 맵 생성기는 아치와 오버행을 **의도적으로** 배치해야 한다.

**다리가 둘인 아치는 하나를 끊어도 버틴다.** 남은 다리로 `BEDROCK` 에 연결되어 있기 때문이다.
이건 버그가 아니라 규칙이며, "두 번째 다리를 끊는 순간 전부 무너진다"는 긴장을 만든다.

**전역 flood fill은 519k 셀이라도 numpy/TypedArray로 수 ms다.** 턴당 1~2회라 비용이 문제되지 않는다.

## 7. 결정론

### 7.1 난수

`Math.random()`, `random.random()` 절대 금지. 상태에 담긴 시드로 해시를 계산한다.

**모든 시프트는 논리(부호 없는) 시프트다.** 아래 의사코드의 `>>>` 는 JS 의 `>>>` 이고,
Python 에서는 `& 0xFFFFFFFF` 로 uint32 를 유지한 뒤 `>>` 하는 것과 같다.
`docs/simulation.md` §2.2 가 좌표·속도에 요구하는 **산술** 시프트와 다르다 — §7.1.1 참조.

```
hash32(seed, x, y, step):
    v = uint32( seed ^ (x * 0x9E3779B1) ^ (y * 0x85EBCA77) ^ (step * 0xC2B2AE3D) )

    h = 0x811C9DC5                                    // FNV-1a offset basis
    for b in [v & 0xFF, (v>>>8) & 0xFF, (v>>>16) & 0xFF, (v>>>24) & 0xFF]:  // 리틀엔디언 4바이트
        h = uint32( (h ^ b) * 0x01000193 )            // FNV-1a prime

    h = uint32(h ^ (h >>> 15))                        // ← 최종 확산. 생략하면 안 된다
    h = uint32(h * 0x2545F491)
    h = uint32(h ^ (h >>> 13))
    h = uint32(h * 0x85EBCA6B)
    h = uint32(h ^ (h >>> 16))
    return h                                          // 항상 uint32 로 반환한다
```

### 7.1.1 산술 시프트와 논리 시프트를 섞으면 절반의 셀에서 해시가 달라진다

`docs/simulation.md` §2.2 는 "JS에서 `|0`, `Math.trunc()`, `/` 사용 금지. `>>`와 `Math.imul()`만 쓴다"고
못박는다. 그 규칙은 **부호 있는 좌표·속도의 floor 나눗셈**을 위한 것이고, 해시에 그대로 적용하면 틀린다.
JS 의 `>>` 는 ToInt32 를 거쳐 **부호 확장**하기 때문이다.

`h = 0x80000000` 에서 실측:

| 식 | 결과 |
|---|---|
| `h ^ (h >>> 15)` (논리 — 옳다) | `0x80010000` |
| `h ^ (h >> 15)` (산술 — 틀렸다) | `0x7FFF0000` |

`h ≥ 2^31` 인 **약 절반의 셀**에서 값이 완전히 달라지고, 그 차이가 이후 곱셈으로 전파되어
`h & 1`(방향 비트)이 뒤집힌다. 즉 1턴차부터 체크섬 불일치가 상시 발생한다.

| 용도 | 시프트 | 이유 |
|---|---|---|
| 좌표·속도 나눗셈 | **산술** `>>` | 음수에서 floor 여야 한다 (`simulation.md` §2.2) |
| 해시·체크섬 비트 연산 | **논리** `>>>` | uint32 를 유지해야 한다 |

`tools/sandbox/automaton.js` 는 논리 시프트로 구현되어 있다.
`harness.mjs --hash` 가 이 성질을 상시 검증한다 — 산술 시프트로 바꾸면 즉시 실패한다.

> ### ★ 최종 확산 단계를 생략하면 방향 선택이 무작위가 아니다
>
> FNV-1a 는 **하위 비트로 확산되지 않는다.** 곱수 `0x01000193` 이 홀수이므로 곱셈이 bit0 을 보존하고,
> 결과적으로 `h & 1` 이 입력 비트들의 **순수 XOR 패리티**가 된다. 실측:
>
> - `h & 1` 을 입력 비트 패리티로 **100.00% 예측 가능** (200,000 표본)
> - `step` 을 1 올리면 격자 **전체**의 방향 비트가 동시에 반전 — 즉 방향장이 평생 단 2가지 배치만 갖는다
> - 결과: 어떤 셀이 필요한 방향을 두 스텝 연속 못 받는 일이 생기고, 옛 정착 판정과 겹쳐
>   더미가 사면 중간에 얼어붙었다 (SCREE 55°, 기대 45°)
>
> 확산 단계를 붙인 뒤: 선형 예측 50.01%, `step+1` 반전율 0.47~0.53, 인접 열 동일 비율 50.1%.
> `harness.mjs --hash` 가 이를 상시 검증한다.

**용도별 비트 배정**

| 용도 | 식 |
|---|---|
| 좌우 방향 선택 | `h & 1` |
| `slideChance` 게이트 | `((h >> 8) & 0xFFFF) < (chanceQ8 << 8)` |
| 우선순위 tiebreak | `h & 0xFFFF` |

`chanceQ8 << 8` 이 2의 거듭제곱 스케일이라 언어 간 차이가 없다.
`chanceQ8 = 0` → 임계 0 → 절대 통과 못함. `chanceQ8 = 256` → 임계 65536 → 항상 통과. 경계가 정확히 맞는다.

**게이트는 `step` 을 쓰지 않는다 — 확정 규칙이다** (`decisions.md` A1).
게이트만 별도 해시를 쓴다: `hash32(seed ^ 0x9E3779B9, x, y, 0)`.
`step` 이 없으므로 활강 가능 여부가 **위치로 고정**되고, 그래서 `slideChance` 가 안식각을
실제로 조절한다. 시드를 섞는 이유는 방향 비트(`h & 1`)와의 상관을 끊는 것이다.
§5.1 의 가동 판정에도 이 게이트를 포함해야 한다 — 안 하면 정착이 영원히 성립하지 않는다.

**`step` 과 `seed` 의 정의**

- `step` 은 **자동자 스텝 카운터**다. 탄도 틱(60Hz)과 다른 카운터다.
  `docs/simulation.md` §2.3 참조. `SUBSTEPS` 와 무관하게 스텝마다 1 증가한다
- **`step` 은 턴의 `PHASE_SETTLE` 시작 시 0 이고, 그 턴이 끝날 때까지 계속 증가한다.**
  §6.1 의 정착 재개에서 **리셋하지 않는다.** 리셋하면 재개 구간이 직전과 동일한 해시 시퀀스를
  반복해 붕괴 패턴이 눈에 보이게 반복되고, 재개 횟수가 상태로 남아야 한다.
  계속 증가시키면 `MAX_SETTLE_STEPS` 예산 공유와도 자연히 맞는다
- `seed` 는 `turnSeed` 이고 **`mapSeed` 와 `turnNo` 에서 순수 파생된다** (`decisions.md` B2):
  ```
  turnSeed = hash32(mapSeed, turnNo, 0, 0)
  ```
  서버 난수가 아니다. 그래서 리플레이가 `mapSeed + intents[]` 만으로 재현되고,
  `netcode.md` §5.2 의 `turnResolve.turnSeed` 는 **표시·검증용 참고값**이다 —
  수신 측은 직접 파생해 대조할 수 있고, 그래야 서버가 몰래 다른 시드를 밀어넣을 수 없다

**상태를 갖는 PRNG 스트림을 쓰지 않는다.** 스트림 방식은 호출 순서가 결과를 바꾸므로 벡터 구현에서 재현이 불가능하다.
**위치와 스텝만으로 결정되는 순수 해시 함수**여야 벡터화와 결정론이 동시에 성립한다.

JS 구현 시 `Math.imul()`과 `>>> 0`으로 32비트 연산을 강제한다. numpy는 `np.uint32`로 고정한다.

### 7.2 체크섬

정착 완료 시점에 격자 전체의 체크섬을 계산한다.

```
FNV-1a 32bit, 격자 바이트 배열 전체를 idx 오름차순으로
h = 0x811C9DC5;  for i in 0..518399:  h = uint32((h ^ grid[i]) * 0x01000193)
```

- **격자만 포함한다.** 활성 행 마스크와 스텝 카운터는 §5.2 대로 턴을 넘기지 않으므로 상태가 아니다
- 서버는 매 턴 체크섬을 브로드캐스트한다
- 클라이언트가 불일치를 발견하면 전체 지형 리싱크를 요청한다. `docs/netcode.md` §4
- 불일치는 **버그**다. 조용히 복구만 하지 말고 텔레메트리로 반드시 보고한다

### 7.3 금지 목록

`sim/terrain` 안에서 금지:

## 8. 폭발 카빙

```
carve(cx, cy, radiusCells) -> { removed, converted }
```

**인자는 셀 좌표와 셀 반경이다.** subpx → 셀 변환은 호출자(폭발 레이어)가 `>> 5` 로 수행한다
(`CELL_SUBPX = 32`). `sim/terrain` 안에서 단위 변환을 하지 않는다.

**판정식 — 제곱 비교로 `isqrt` 를 피한다.**

```
재질별 유효반경   rm = (radiusCells * RESIST_Q8[mat]) >> 8
제거 조건        dx*dx + dy*dy <= rm * rm
```

| 재질 | `RESIST_Q8` | 유효반경 (반경 40 기준) |
|---|---|---|
| `SAND` | 256 | 40 |
| `SOIL` | 208 | 32 |
| `SCREE` | 256 | 40 |
| `ROCK` | 140 | 21 |
| `BEDROCK` | — | 판정 이전에 제외 (저항 ∞) |

이 값은 **잠정값이다.** 무기별 데미지·반경과 함께 밸런싱된다 (`docs/game-design.md` §6.1).

절차:

1. `BEDROCK` 을 제외하고 반경 내 셀을 순회하며 위 판정으로 제거
2. **가장자리를 부드럽게 처리하지 않는다.** 거리 비교만으로 자른다. 부드러운 경계는 렌더러가 만든다
3. 제거된 셀 = `EMPTY`
4. 카빙 영역 `y0-2 .. y1+2` 를 활성 영역에 등록

**동시 턴이므로 여러 폭발이 같은 틱에 적용된다.** 순서를 명시적으로 고정한다.

```
플레이어 슬롯 번호 오름차순으로 carve 전부 실행
  → 연결성 검사 1회 (§6.1, 무조건)
  → 정착 시작
  → 정착 후 연결성 검사 1회 더. 변환이 있으면 정착 재개
```

**슬롯 순서로 고정하는 이유:** 착탄 시각 순으로 하면 시각 계산에 정수 오차가 개입할 여지가 생긴다.
슬롯 번호는 명백히 결정적이고 두 구현이 다를 수 없다.

### 8.1 흙 쌓기 — `deposit`

적층탄(`game-design.md` §6.1)이 요구하는 유일한 **지형 추가** 연산이다.

```
deposit(cx, cy, radiusCells, mat) -> 채운 셀 수
```

- **반경 내 `EMPTY` 셀만 채운다.** 비-`EMPTY` 를 덮어쓰지 않는다 — 덮어쓰면 `BEDROCK` 을
  지우거나 `ROCK` 을 `SOIL` 로 바꿀 수 있고 그건 §2 위반이다
- 판정식은 `carve` 와 같은 제곱 비교. **재질 저항은 없다** (쌓는 쪽이라 저항이 무의미하다)
- 쌓은 영역을 활성화한다 → 자동자가 곧바로 안식각까지 흘러내린다.
  즉 "벽"이 아니라 "더미"가 생긴다. `SOIL` 로 쌓으면 40.3° 언덕이다
- **연결성 검사를 부르지 않는다.** `ROCK` 을 만들지 않으므로 §6 과 무관하다

## 10. 미결 항목

**임의로 확정하지 않는다.** 각 항목의 선택지와 실측 근거는 `docs/decisions.md` 에 정리했다.

1. **초기 지형 생성 알고리즘** — 어느 문서에도 없다. `mapSeed` → 격자 매핑이 비트 단위로 같아야 하는데
   명세가 없으면 1턴차에 바로 체크섬 불일치가 난다. 좌우 경계를 막는 규칙(§1.1)도 여기서 정해진다
2. **시간 압축 스케줄 곡선** (§5.2)
3. **`SUBSTEPS`, `MAX_SETTLE_STEPS` 확정값** (§4.1) — 동시 폭발 간격 스윕이 남았다 (`decisions.md` A3)
4. **물 재질** — 붕괴와 상호작용이 재밌지만 자동자 규칙이 크게 복잡해진다. Phase 4 이후
5. **`SCREE` 변환 시 원래 `ROCK` 의 지층 색을 유지할지** (렌더링과 연동)
6. **적층탄이 필요한 `deposit()` 연산** — §8 에는 제거만 있고 추가가 없다 (`game-design.md` §6.1)
7. **`CONNECTIVITY_MAX_ROUNDS`** (§6.1) — 재개 루프 상한. 통상 2회로 끝나지만 상한이 없으면 안 된다
8. **`step()` 의 표현 전용 산출물** — `docs/rendering.md` §5 의 모래 입자는 "이동한 셀" 목록을
    전제하는데, §5.2 가 "상태는 격자 하나뿐"으로 정해 그 목록을 내주는 곳이 명세에 없다.
    반환값으로 정의할지(상태도 체크섬 입력도 아님), 렌더러가 활성 행 안에서 샘플링할지

### 11.2 실전 규모 폭발 1발 — `SUBSTEPS` 를 정하는 근거

`layers` 프리셋 지표면 명중, 정착까지.

| 반경(셀) | 제거 셀 | 정착 스텝 | 순수 sim | 이동 누적 | `SUBSTEPS=4` 벽시계 | 3초에 맞추려면 |
|---|---|---|---|---|---|---|
| 12 | 283 | 319 | 8 ms | 1,724 | 1.3 s | 2 |
| 20 | 790 | 610 | 24 ms | 4,793 | 2.5 s | 4 |
| 30 | 1,888 | 860 | 53 ms | 11,651 | 3.6 s | 5 |
| 40 (기본) | 3,374 | 1,235 | 102 ms | 25,792 | 5.2 s | 7 |
| 60 | 6,916 | 1,652 | 205 ms | 51,875 | 6.9 s | 10 |
| **80 (최대)** | 12,043 | **1,881** | 300 ms | 75,886 | 7.8 s | **11** |

**읽는 법.** 순수 sim 시간은 전부 0.6초 이하라 **계산은 싸다.**
문제는 `SUBSTEPS=4` 로 보여주면 프레임 수가 너무 많다는 것이다.
단발 최악(반경 80)은 `SUBSTEPS = 17` 로 3초에 들어가지만, **실전에서는 여러 명이 동시에 쏘므로
§11.6 의 동시 폭발 최악이 하한을 정한다.**

재현: `node tools/sandbox/harness.mjs --blast`

### 11.3 대형 붕괴 (화면 1/4) — 로드맵 완료 조건은 이 규모로 판정하지 않는다

`ROCK` 선반이 다리 하나로만 `BEDROCK` 에 붙어 있고, 그 위에 129,920셀(격자의 25.1%)의
`SAND`/`SOIL` 을 올린 무대에서 다리를 끊는다.

| 항목 | 값 |
|---|---|
| 부유 흙 | 129,920셀 (25.1%) |
| `ROCK` → `SCREE` | 8,960셀 |
| 정착 | **27,249스텝** (수렴한다) |
| 이동 누적 | 19,038,501회 |
| 스텝당 | 0.43 ms |
| 순수 sim | 11.7초 |
| 격자 밖 유출 | 2,280셀 |
| `SUBSTEPS=4` 벽시계 | 113초 |

**수렴은 하지만 비용이 수송 거리에 지배된다.** 셀은 스텝당 1칸만 움직이고, 26.6° 로 퍼지려면
밑변이 1,020셀이라 화면 폭(960)을 넘는다. 정점의 흙이 500셀 넘게 수평 이동해야 하고 그게 줄을 선다.
(이전 판에서 200,000스텝에도 미수렴이었던 것은 `slideChance` 가 192/38 이고 step 게이트였기 때문이다.
정적 게이트로 바꾸자 115,029 → 27,249스텝으로 4배 빨라졌다.)

**이 규모는 실전에서 나오지 않는다.** 가장 큰 무기의 반경 80이 12,851셀이므로 10배 차이다.
그래서 로드맵 Phase 0 의 완료 조건은 "화면 1/4" 이 아니라 **§11.2 의 최대 무기 반경 + §6.2 아치 붕괴**로
판정해야 한다. `docs/roadmap.md` 를 그렇게 고쳤다.

### 11.5 구조 붕괴 (§6.2 의 실증)

`arch` 프리셋 — `ROCK` 아치가 다리 **둘**로 `BEDROCK` 에 붙어 있고 위에 모래 담요가 있다.
다리 폭이 49셀이므로 폭발이 다리 폭을 전부 덮는 행이 하나는 있어야 절단된다
(반경 46 → `ROCK` 유효반경 25 → 중심 행에서 51칸). **중심을 벗어나면 양 끝 몇 열이 살아 절단되지 않는다.**

| 단계 | `ROCK`→`SCREE` | 천장 잔량 | 정착 |
|---|---|---|---|
| 초기 정착 | — | 9,674셀 | 15,991스텝 |
| 왼쪽 다리 절단 | **0셀** | 9,674셀 | — |
| 오른쪽 다리 절단 | **28,511셀** | **0셀** | 2,475스텝 |

**다리 하나로는 버틴다.** 남은 다리로 `BEDROCK` 에 연결되어 있기 때문이다(§6.2).
두 번째를 끊는 순간 28,511셀이 한꺼번에 `SCREE` 가 되어 전부 무너진다.
`overhang` 프리셋의 캔틸레버 슬랩(11,840셀)은 지지 기둥 1발로 16,265셀이 변환되어 완전히 붕괴한다.

### 11.6 동시 폭발 — `SUBSTEPS` 하한을 정하는 표

`game-design.md` §4.1 이 동시 턴이므로 인원 2~6 이 매 턴 동시에 쏜다.
반경 40 폭발을 지표면에 균등 간격으로 배치했다 (`harness.mjs --simultaneous`).

| 발수 | 간격 | 제거 셀 | 정착 스텝 | 1발 대비 | 3초에 필요한 `SUBSTEPS` |
|---|---|---|---|---|---|
| 1 | — | 3,374 | 1,235 | 1.00× | 7 |
| **2** | **320** | 7,307 | **4,846** | **3.92×** | **27** |
| 3 | 240 | 10,583 | 2,441 | 1.98× | 14 |
| 4 | 192 | 13,412 | 3,961 | 3.21× | 22 |
| 6 | 137 | 20,938 | 3,636 | 2.94× | 21 |

> **비단조다. 최악은 발수가 아니라 간격이다.**
> 크레이터가 멀리 떨어져 있으면 각각이 장거리 수송을 독립적으로 해야 해서 비싸고,
> 촘촘하면 크레이터가 합쳐져 지형이 고르게 낮아지므로 오히려 싸다.
> 즉 "인원이 많을수록 비싸다"가 아니라 **"적당히 흩어져 있을 때 가장 비싸다."**
>
> 따라서 `MAX_SETTLE_STEPS` 와 `SUBSTEPS` 를 **발수로 산정할 수 없다.**
> 관측 최악은 2발 간격 320 의 4,846스텝이지만 간격을 촘촘히 스윕하지 않았으므로
> 더 나쁜 조합이 있을 수 있다. `decisions.md` A3.
